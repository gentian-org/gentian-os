# Architectural decisions

The decisions that set the direction of the architecture cleanup. Each one
is stated once here and referenced by number from the plans; the plans hold
the detail. A decision changes by editing its entry, not by contradicting
it elsewhere.

| AD-1 | The nine rules in [security-principles.md](../security-principles.md) are normative. A change that breaks one needs a written reason. Every request passes exactly one named enforcement point — gateway, publishing proxy, director, custodian, MCP gateway — and apps never decide platform questions. **One accepted limit, stated here.** On a public entry that passes its callers' credential to the app (AD-6, `authMode: app`) the publishing proxy is still the one enforcement point, and what it enforces is the declared paths, the stripped headers and the rate limit — not who calls. The credential is one the app issued (an app password, an API key, a token of the app's own), only the app can check it, and the platform neither knows the caller nor sees the credential's owner. So a person removed from the tenant keeps access through such a credential until the app itself revokes it; removing them from the realm ends their sign-in and does not end that. The tenant's perimeter approver is told this before approving such an entry. Closing it needs credentials the platform issues and can revoke, which is not built ([roadmap.md](../roadmap.md) 1.34). **Changed 2026-10-09**: the limit is stated; it came with the entry type. | security-principles.md |
| AD-2 | The **director** is the only process that writes to `gentian-deployments`. Every write is authenticated by Keycloak and authorised by OpenFGA; commits are signed and Argo CD (`AppProject.spec.sourceIntegrity`, GnuPG mode `head`) syncs only commits signed by the director or the break-glass key. The **operator** writes to the cluster only and never holds a git credential. Git is thereby the trusted, audited source of cluster configuration. | [operator-split-plan.md](operator-split-plan.md) |
| AD-3 | **What lives outside the cluster is the App Store's data, not its interface.** The store is a service outside the cluster, run by a vendor. It holds and serves the data about apps: metadata, descriptions, pictures, reviews, evaluations and reports, editions and versions with their build digests, prices, and the record of what a tenant has acquired. The store's interface, and everything that happens when a button is pressed, are an app **on** the cluster: the **App Store app** (component `app-store`), a platform UI of its own, installed per tenant, its tile shown only to people who may install apps in that tenant. It renders what it fetches from the store's API, and it treats that content as data — plain text, a restricted Markdown subset, images by address — never as code: no HTML, no script and no frame from a store. It does the installing on the cluster's side, under the signed-in person's own token, through the director and the custodian, which ask of it what they ask of every other caller. **The cluster always calls out; the store never calls the cluster**, holds no credential for one, and has no page inside the cluster's interface. There is no message bridge between a framed vendor page and the cluster: that design is withdrawn, because it put a vendor's page and the logic of installing on the desktop, which is every member's app. **The store decides nothing for the cluster, and the cluster does no licence gating.** There are no entitlements: no statement a store signs, no store key pinned on a cluster, no relation for a tenant's right to an entry. **Supply is controlled at the source.** When a tenant acquires an app the store mints a credential for the repository that holds its chart and images, and that repository checks it on pull. The App Store app receives the repository's address and the credential in the store's confirmation, declares the repository through the director, sets the credential through the custodian, and installs with `{coordinate, digest, defaultGrant}`; a free app's confirmation carries no credential. On the cluster the credential — a user name and a password, for a repository of `type: oci` — becomes one pull Secret in that tenant's app namespace and in no other, and a chart whose address lies inside exactly one repository the tenant declared is pulled with it; a chart inside more than one is not installed until the tenant narrows one. Holding the credential is what makes a private app arrive, not a guarantee that it cannot be run elsewhere on the same cluster: the chart installer is one process and caches charts by name and version, so a chart one tenant pulled can be installed by another until it restarts, and an image already on a node can be started by any pod that does not force a pull. The credential is not disclosed by either; the artefact is. The OS decides nothing in this: whether something has been paid for is the business of whoever sells it, and is enforced where the thing sold is handed over. A second copy of that decision inside the platform could only drift from the one that counts, and a platform meant to run with no store at all would have to switch a gate off rather than not have one. The director asks one question of an install — may this person install apps in this tenant (`can_install_app`) — and a second, `can_grant`, of an install made for everyone, which says so in the same request and the same commit (`defaultGrant` on the app's entry); the operator then grants the app to the tenant's members once, when its group exists. **Payment never passes through the cluster**: for a paid acquisition the store answers with a checkout address at the vendor, which the app opens in a separate window, and the app then asks the store for the outcome. **The digest still pins the build**: a profile bundle is one file, the profile and the few other objects the app needs on a cluster beside it, and the digest pins the profile and its companions — not the chart or images it names. The store's confirmation carries the content digest of the profile bundle, the install request carries it, the bytes the catalogue serves are refused unless they hash to it, and the director records it in git as a field of the install — never as part of the app's name. That fetch, of one profile at the digest an install names, is the only way a profile reaches a cluster (AD-14). The operator checks it again before it rolls anything out: the director commits the verified bytes beside the profile, and a Component pinned to a digest is rendered only when those bytes hash to it and the profile in the cluster, and every companion, is what they say. A store can therefore lie about what an app is and cannot change which bytes are installed. **The store depends on licence reporting** ([operations.md §6.2](../design/operations.md)): a cluster with reporting off has no App Store app. **Browsing needs no sign-in**: the store's catalogue is readable with no account and no token, and the App Store app shows it at once; an anonymous read tells the store only the address the request comes from, and the app sends no cluster or tenant identifier with it. A tenant's administrator signs in to the store, with an account at the vendor and stating the address of the tenant, only for what concerns the tenant — to acquire an app and to see what the tenant has acquired. A store that has no reports for that address refuses those calls, with a reason the app shows, and the catalogue stays readable; a cluster with no subscription is shown the terms of the free licence. Nothing on the cluster is blocked by any of it. **Without a store, apps are installed by command only** (AD-14). **Changed 2026-10-06** from "the App Store runs outside the cluster" as a whole — a vendor page in a window on the desktop, asking the desktop to install through a message bridge. What was right in it stays: the data is outside, the digest pins, the OS gates nothing. What changed is where the interface and the installing are. | [store-contract.md](../design/store-contract.md), the API format in [artefacts/store-api.md](artefacts/store-api.md) and [artefacts/store-api.openapi.yaml](artefacts/store-api.openapi.yaml), [ui-restructure.md](ui-restructure.md) §3, [target-component-structure.md](target-component-structure.md) |

| AD-6 | **Exposure carries a mandatory `authMode`** with no default, and a `surface` of `gateway` or `perimeter`. A perimeter surface is a capability the profile declares; a proxy exists in `tenant-<t>-dmz` only for a surface a **perimeter approver enabled**, within cluster policy, with that tenant's credential. The relation asked is `can_expose`, never `admin`, so publishing is always its own audit line. **Who holds it**: the members of the tenant's group `gentian:tenant:<t>:perimeter`, which exists from the day the tenant does; the cluster's administrator, in every tenant its cluster operates (`operated_by` — a tenant that withdrew the operator is not approved for by the cluster's administrator); and the tenant's own administrators **only where the cluster's administrator switched that on** for the tenant (`Tenant.spec.perimeter.adminsApprove`, off by default, set when the tenant is created or afterwards, beside AD-14's switch for adding catalogues and like it never by the tenant's own administrator). One tenant starts with the switch on: the user tenant of a single-tenancy cluster, created by the install or by the director's create route when the request does not say otherwise, where the cluster has one tenant for users; the cluster's administrator can turn it off there as anywhere. Git holds the switch (AD-12): the operator projects it into the store, and removing it from the manifest removes the grant. Who is in the perimeter group is changed only by somebody who may approve. Where the instance runs does not enter into it: shared and public are independent, and nothing is published by default. **What the platform does for a perimeter entry is one of two things, and `authMode` says which.** `none`: the declared paths are forwarded for anyone and no credential is passed on — the proxy removes `Authorization` and `Cookie`. `app`: the same, except that the caller's `Authorization` header is passed to the app as sent, because the callers hold a credential the app issued and only the app can check it; the proxy checks nothing, cookies still do not pass in either direction, and such an entry is held to a lower rate per client address (5 requests a second, 50 more at once, 20 at a time, against 20, 200 and 100), answered with 429 beyond it. **An approval is of a kind**: the registry records whether an entry was approved as a public address, as a public address that passes the credential, or as an entry behind sign-in that keeps the app's own `Authorization` header (AD-13), and the operator acts on an approval only while the profile's entry still declares that kind — a catalogue entry that later asks for more is a request again. **The modes that promised a check nobody makes are withdrawn**: `basic`, `signature`, `jwt` and `bearer` are refused on a perimeter entry by the schema. Verifying a password needs a credential store the platform does not have, and a webhook signature needs a verifier per provider; a Keycloak token could be verified at the perimeter Gateway, but the only token that names an app as its audience is the one the front door exchanges for a signed-in person (`exchangeToken`), and no client exists for a caller without a browser to obtain one, so there is no token such a check could soundly require of the callers a public entry is for. They return when they can be enforced ([roadmap.md](../roadmap.md) 1.34). **Changed 2026-10-09**: `authMode: app` and the recorded kind are added, and the four unenforced modes are withdrawn; before, every mode but `none` was descriptive and the proxy dropped the credential whatever the entry said. **Changed 2026-10-09**, who holds `can_expose`, from "the tenant's admins hold that relation by default, because most tenants do not staff the role separately": that default was never built — only the members of a `perimeter` group nothing created could approve — and the owner decided against building it: the group is created with the tenant, the cluster's administrator approves, and a tenant's administrators approve only by the switch. **Changed 2026-10-09**: the install writes the user tenant of a single-tenancy cluster with the switch on; before, it was off there as everywhere. **Changed 2026-10-09**: the director's create route writes that tenant the same way when the request does not state the switch, and keeps an explicit off; before, a user tenant created by command started with it off. | [target-component-structure.md](target-component-structure.md) §8, [namespace-cleanup.md](namespace-cleanup.md) §2.6 |

| AD-10 | **The portal splits two ways**: the tenant desktop — frontend bundle and its BFF, one image — runs in `tenant-<t>` with only that tenant's credentials; **the platform is a tenant** — `Tenant/platform` adopts the kernel realm and has a desktop in `tenant-platform` like every other tenant. **The desktop is the desktop, for everyone**: what differs between a platform administrator, a tenant administrator and a member is the tiles their relations grant, never the image. A member sees apps. An administrator sees the administration console, the App Store app, and links to what they administer — identity, the cluster dashboard, subscriptions — and never both sets: least privilege is per account, and administrator and member are disjoint roles ([roles-and-authorizations.md](roles-and-authorizations.md) §1). **The desktop is a relay for tiles**: it shows what the signed-in person may open and opens it. It carries no install, uninstall, add-on, access, repository or store logic, because it is the app of people who hold no privilege and must hold no administrative code path. **The administration console is an app**: a component installed for every tenant from its own profile and built from the app template, not a mode of the desktop; installed apps are administered there. **The App Store app is an app too** (AD-3): a platform UI of its own beside the desktop and the console, which renders the data of the store outside the cluster and installs through the director and the custodian. No page of a store is shown inside the cluster's interface, and the desktop is asked nothing on a store's behalf. A link to something that runs elsewhere is a component too, one that runs nothing and carries a tile. Nothing with authority leaves `kernel-control`; nothing without authority stays in it. The current single BFF holding every tenant's credentials is retired. Nothing of the portal is shared: the frontend holds no state, so serving it per tenant costs nothing and keeps it on the tenant's own origin; the BFF holds one tenant's UI state on one tenant's origin, which is exactly what AD-4 says a shared instance may not hold until certified. It holds no client secret: the edge is the only session authority (AD-13). | [namespace-cleanup.md](namespace-cleanup.md) §2.5, [ui-restructure.md](ui-restructure.md) §2 |

| AD-12 | **The authorization store is a projection; Keycloak's events are the only source of membership in it.** Group membership is stored in OpenFGA as `group#member` tuples written by the **operator** from the signed statements Keycloak's event listener sends it, and reconciled toward Keycloak with a read-only client — never edited in place; contextual tuples carry runtime facts only (task TTL, `acting_for`, device posture). This is OpenFGA's own hybrid guidance and the Zanzibar shape: access reviews and reverse queries are native, checks are lookups, and no group travels in a token for a platform decision. Structure — role-to-group assignments, tenants, installs, grants — is projected by the operator too, from what git declares, once Argo CD has applied it. **The operator projects; the director asks.** The director asks the store before every call it serves, and writes git. It writes to the store only what one of its own routes is itself responsible for recording there — a fact that is neither declared in git nor held by Keycloak — and nothing else; today no route records any, so everything the director changes reaches the store through git and the operator. **Git holds the defaults, and everything beyond them is an action through the director.** The conventional tuples a tenant starts with — its admins group holding `admin`, the cluster holding `operated_by` — follow from what git declares, so they can be derived and checked; every later grant or revocation is an act somebody took, recorded when it happened and reconstructible from nothing else. The store is therefore not rebuilt on start: at bootstrap the director **checks that the defaults git implies are still the defaults the store holds** and reports the difference. A store that has diverged is a question, not a merge — rewriting it would erase exactly the acts that are not derivable. The polling bridge with its admin credential is retired. The single vocabulary is [authorization-model.md](authorization-model.md). Because apps still read groups from their own tokens, **the aim is that a membership change revokes the user's sessions and that offline tokens are disabled**; access tokens stay short-lived. Neither is what the platform does today: an app that read a person's groups from its own token keeps them until that token or the app's own session ends. **Changed 2026-10-09** from "written by the director from Keycloak's event stream" and "structure is written by the director from CRs in the same operation as the commit it reflects; the operator only reads it". The operator was built as the one process that projects, so that the director, which decides who may make a call, needs no right to rewrite the answer; the entry now names it. **Changed 2026-10-09**, sessions and offline tokens, from "a membership change revokes the user's sessions; access tokens stay short-lived and offline tokens are disabled": no code did either, and the owner decided that the entry states both as an aim and not as something the platform does. Two things this entry says are not built and are listed in [open-items.md](open-items.md): nothing reconciles the stored memberships toward Keycloak, with a read-only client or any other; and the check of the defaults at start does not exist. And one thing stands against it: the operator, which writes the store, also holds Keycloak's master administrator credential. | [roles-and-authorizations.md](roles-and-authorizations.md) §3 |
| AD-13 | **The edge is the only session authority.** One confidential OIDC client per tenant zone, on the `authenticated` Gateway, mints the one edge cookie; **no platform component downstream runs a code flow or holds a client secret**. The gateway forwards the edge token only on a route whose exposure entry sets `forwardToken` — the desktop, which needs it to call the director — and every other backend receives identity headers the gateway sets after stripping inbound ones. **One entry type leaves the `Authorization` header to the app, and it changes nothing about the session.** An app whose own pages send a token of the app's in that header declares `clientAuthorization: app` on its gateway entry; once the tenant's perimeter approver has approved that entry (`can_expose`, in the same registry and by the same route as a public address — it is not one, and nothing is published), the gateway neither puts the edge's token into the header nor removes what the browser sent. The session is required as before: the OAuth2 filter still demands its own cookies on every request and no bearer stands in for them, the bouncer still asks whether this person may use the app, and it is shown the session as the ID token in a header the filter owns and the bouncer removes. No platform token reaches the app, and `clientAuthorization` excludes `forwardToken` and `exchangeToken` across a component. Until approved the entry is an ordinary one and the Component says so (`ClientAuthorization`); an app that keeps a session of its own runs a silent login with **its own client and audience**, so no app ever holds a token valid at the director or at a sibling. Envoy Gateway's OIDC filter has no back-channel logout and keeps no server-side session, so **ending a session at Keycloak is what ends it**: the edge holds a short-lived access token and refreshes it, and a refresh against an ended session fails. The bound on how long a signed-out person is still let through is the access token's lifetime, which the realm sets — so that lifetime is the control, and it is minutes rather than the twelve hours it once was. The director records nothing and the bouncer asks nothing: an earlier design had the director write `session:<sid>#revoked` for every bouncer replica to read, and it was removed because it cost a round trip on every request to answer a question the token's own expiry already answers. The cost of this choice is that sign-out is not instantaneous; the thing to change if that ever matters is the access-token lifetime, not the addition of a list. The L2 decision cache is keyed on `(sub, sid, route)` — the session, not the token — so a refresh is not a miss and a revocation can be evicted. The hard bound on what a user may do *inside* an app is the app's own session, which a profile caps with `sessionMaxAge`; the edge bounds reachability, not an app's captured group model. **Two exceptions, each named here, and no others.** **The first is the App Store app's sign-in to a store outside the cluster** (AD-3). A tenant's administrator signs in at the store's own issuer, and the App Store app runs that authorization-code flow although it is a platform component behind the edge. It is acceptable because, and only while, three conditions hold: (a) the code is exchanged by the App Store app's backend on the cluster and the resulting store token is kept there, bound to the administrator's cluster session, and never handed to the browser — the app is a public client with PKCE and still holds no client secret; (b) the store's issuer redirects to exactly one address per tenant, the App Store app's own callback, and to no other host or path under the tenant's address; (c) a repository credential is released by the store only to a token carrying the scope `store.acquire`, never to one that can only read. The token this flow yields is valid at the store and nowhere on the cluster, it establishes no session with the platform, and it is not what pulls images. **The second is the sign-in sidecar** (`requires.services.identity.sidecar`). Beside an app that supports neither OIDC nor SAML the platform runs a small service of its own, which makes the app's session for a person the tenant's realm vouches for. One route of the app's host reaches that service without a session: `/sso/acs`, by POST and by that exact path, with the identity headers a client could send removed. Keycloak's signed answer arrives there from the realm's own address, and the edge's cookies do not travel with such a request. It is acceptable because, and only while, four conditions hold: (a) the service accepts only an answer signed by the tenant's realm, for a request it sent itself, brought back by the same browser, about the same person the edge admitted when that request was sent — a sign-in begins at `/sso/login`, which is behind the edge's session and the bouncer, so **who may use the app is still decided by the edge**; (b) it holds no client secret and no platform credential: it has what its handler needs of the one app it stands beside, and nothing that is valid at the director, at another app or at the realm; (c) the session it establishes is the app's own, lasts at most one hour and no longer than the person's session at the realm, and is a session with that app alone; (d) the handler it runs is the one in the app's profile bundle, from a catalogue of the whole cluster, for an install pinned to that bundle's digest, and it is never run for a tenant that signs in in the kernel realm. What it costs is stated with it: the service can make a session for anybody in its app, the identity headers it is given at `/sso/login` are unsigned and are kept honest by network rules alone, and an app session can outlast a sign-out by up to its hour where the app cannot be told of the sign-out or was not told ([security.md §2.12](../design/security.md)). Neither exception covers another component, and neither signs anybody in to the platform: **the cluster's own sign-in stays the edge's alone.** **Changed 2026-10-09**: the sign-in sidecar is named as the second exception. It was built, and is declared by three apps, before this entry said so; the entry now states the conditions it was built to. **Changed 2026-10-09**: an approved gateway entry may keep the app's own `Authorization` header (`clientAuthorization: app`); before, only the Keycloak administration console's route did, and an app's own bearer token was dropped. **Changed 2026-10-09, sign-out**: the cost sentence said an app session outlasts a sign-out by up to its hour, for every app. The realm now tells the sidecar of a sign-out — a signed SAML `LogoutRequest`, posted server to server to the sidecar's own Service inside the cluster, on no route of the edge — and the handler ends the person's sessions in the app. That holds for Docmost and OpenProject. The hour is what is left where it does not: Activepieces 0.28.0, which has nothing to end a session with; a sidecar that was not running when the realm told it, since the realm tells once; and a realm session that ran out without a sign-out. The session-less route (`/sso/acs`) is still the only one: the sign-out path is not reachable from outside the cluster and adds no exception to this entry. | [networking.md](networking.md) §2, §4, [ui-restructure.md](ui-restructure.md) §1; the first exception in [store-contract.md](../design/store-contract.md) §6.1, the second in [security.md](../design/security.md) §2.12 and [iam.md](../design/iam.md) §1.11 |
| AD-14 | **Without a store, apps are installed by command only.** `kubectl gentian apps install` asks the director, on the same route and under the same question as every other install (AD-3). **The cluster renders no catalogue of its own in any interface.** A second, barer shop beside the one that is maintained would be worse at everything a shop is for, and a listing with an install action in an administrative screen is one more place the logic of installing would live. A *catalogue* remains what the director fetches from: an https address serving an index and one profile bundle per file, where the director fetches the bundle a coordinate names and checks it against the digest. **Or a directory of the cluster's own deployments repository**, holding the same index and files, for profiles that must not be public: the director reads it from the checkout it already holds, at the commit that checkout is at, with the credential it already has, and holds what it reads to the digest and to every other rule of this entry. Such a source states a directory and nothing else — no repository, host, branch or commit; a relative path of plain names, no `..`, no symbolic link followed, and never `clusters/<cluster>/catalogue`, where installed profiles are written. Only the cluster's administrator declares one, for the cluster or for one tenant; delegation does not extend to it, because a tenant's administrator does not control the repository. It is trusted as an address the cluster's administrator added and no further. **One bundle, one digest**: a bundle is one file, the profile first and after it the few other objects the app needs on a cluster, and the digest is taken over the whole file, so an install pinned to a digest is pinned to the profile and to everything that came with it. **A profile reaches a cluster in this way and in no other**: nothing copies a catalogue into a cluster ahead of an install, and the ApplicationSet that synced every profile of a git repository (`Repository`, `type: git`, `role: apps`) is retired. (One exception is decided: the installer's default profile, stated at the end of this entry.) A source publishes an index — coordinate, version, edition, trust tier, digest, and nothing a shop would show — and the director still answers it, the **ce** and **pe** entries only, so that an entry's digest can be looked up with no store; no screen lists it, and the console's catalogue view is hidden. **A catalogue exists in one of three ways.** For the whole cluster, added by the cluster's administrator on the Cluster claim (`spec.catalogue.sources[]`): every tenant installs from it. For one tenant, added by the cluster's administrator on that tenant's manifest (`Tenant.spec.catalogue.sources[]`): only that tenant sees it. For one tenant, added by that tenant's own administrator — only where the cluster's administrator has **delegated** that to the tenant, a per-tenant switch that is off by default and that only the cluster's administrator sets. **A new cluster is given one catalogue, chosen by what it is installed from**: the installer writes it into a claim that names none — the released catalogue for a release tag or `main` of the platform, the catalogue under development for any other branch — and does not rewrite a claim that exists. Each is a commit by the director with the person as its author (`can_configure` on the cluster; `can_install_app` on the tenant for the delegated case); the director reads what a tenant sees when it is asked, and another tenant's catalogue does not exist for this one. **An address is checked whoever adds it**: public https only, and the director connects to nothing inside the cluster or the network it is hosted on; for a catalogue in the deployments repository it connects to nothing at all. **A profile says where it came from.** ComponentProfiles are cluster-scoped, so a name is one profile: a tenant's catalogue never takes a name another origin holds and nothing takes a name a tenant's catalogue holds, and a profile from a tenant's own catalogue is installable only in that tenant — refused by the director, and again by the operator at rollout. **Only a catalogue of the whole cluster brings anything beside the profile**: what travels with a profile is an object of the whole cluster or of a platform namespace, where a tenant decides nothing, so a bundle from a tenant's own catalogue is its profile and nothing else, and one that holds more is refused. None of this is a licence, and there is no access mode a store sets on a catalogue: the install itself is asked of the person and of nothing else (AD-3). One install mechanism (fetch the bundle at the digest, apply the profile, commit), whoever asked. **Changed 2026-10-06** from "the cluster lists its sources' entries as installable from its own screen". **Changed 2026-10-09**: the entry names the fields, the bundle and its one digest, the rule for what travels with a profile, and the catalogue a new cluster starts with, as they are built; the decision is unchanged. **One exception, decided 2026-10-09 and built: the installer's default profile.** At install, before there is a director to ask, the installer places the Operations Console's profile in the cluster's catalogue directory (`<catalogue address>/profiles/operations-console.yaml`, or what `GENTIAN_DEFAULT_PROFILES` lists — https addresses of profiles in a catalogue and nothing else; a local file is refused). It is held to this entry's rule in everything but who does the fetching. The installer reads the catalogue's `index.yaml` and takes the digest it lists for the entry, or the digest the person installing pinned (`<address>@sha256:<digest>`), which the index does not override; it writes nothing unless the bytes hash to that digest. **Bytes that do not hash to it stop the install**; so does an index that does not list the entry when nothing is pinned. **A catalogue that cannot be reached is a warning**, and the cluster comes up without the profile. What is written is what the director writes for an install of the same bundle, byte for byte: the bundle as it was served, and beside it the same bytes and the catalogue's origin on the profile; a test holds the installer's files to the director's. The digest, who stated it — the index or the pin — and the address are in the signed commit that carries the profile. **A definition that already holds another build, with its record, is kept and reported, never replaced.** A copy an earlier installer wrote with no record is no decision of anybody's: when its bytes hash to the digest wanted the record is added and the file is left as it is, and otherwise it is replaced by the verified file, and the run says so. **At rollout the operator holds a default to that record.** The Component it creates for a profile that declares itself a default names no digest; the digest is the one recorded with the profile, that of the bundle it carries, and before anything is rendered the profile and every companion are compared with that bundle, as for a Component pinned to a digest. One that differs is held with the same reasons, and what is running stays. A default whose profile the platform's chart ships has no record and is not asked. **What the exception does not give.** A default's digest is stated only on the profile, not apart from it as an install's is on the tenant's manifest, so a profile replaced together with its bundle is not noticed. | AD-15 | **The OS is multi-lingual: every word a person reads is translatable**, and a language is added by adding a message catalogue, never by changing a component. German and English are the catalogues that ship today. Three surfaces, one rule. **The platform's own chrome** — desktop, console, Keycloak's login and account pages — carries a message catalogue per locale and no user-visible string is written inline in a component; Keycloak already ships translations, so its realms enable them rather than restating them. **A component's catalogue text** — the tile label today, and whatever else a person reads later — carries a required fallback plus an optional map keyed by locale (`de_DE`, `en_US`), which is additive: a profile with one language stays one line. **Matching is forgiving within a language and never across one**: `de-CH` is served `de_DE`, because a label in the viewer's language is better than one in another, while an unmatched language falls back to the author's own words rather than to a guess. The viewer's language comes from their account, and from the browser until they have said.
