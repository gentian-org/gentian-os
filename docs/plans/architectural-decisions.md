# Architectural decisions

The decisions that set the direction of the architecture cleanup. Each one
is stated once here and referenced by number from the plans; the plans hold
the detail. A decision changes by editing its entry, not by contradicting
it elsewhere.

| # | Decision | Detail |
| --- | --- | --- |
| AD-1 | The nine rules in [security-principles.md](../security-principles.md) are normative. A change that breaks one needs a written reason. Every request passes exactly one named enforcement point — gateway, director, credential manager, MCP gateway — and apps never decide platform questions. | security-principles.md |
| AD-2 | The **director** is the only process that writes to `gentian-deployments`. Every write is authenticated by Keycloak and authorised by OpenFGA; commits are signed and Argo CD (`AppProject.spec.sourceIntegrity`, GnuPG mode `head`) syncs only commits signed by the director or the break-glass key. The **operator** writes to the cluster only and never holds a git credential. Git is thereby the trusted, audited source of cluster configuration. | [operator-split-plan.md](operator-split-plan.md) |
| AD-3 | The **App Store runs outside the cluster**, operated by Gentian Technologies. The cluster holds no catalogue: it materialises a profile, at a content digest, only when a tenant installs it, through the director. The store may trigger an install and **read** cluster state through the director's read API with the signed-in human's token — it has to, or it cannot show what is already installed and how it is configured — but it never supplies the artefact. Reading is not supplying. | [component-profile.md](component-profile.md), [app-store-schema.sql](app-store-schema.sql) |
| AD-4 | One catalogue kind, **`ComponentProfile`**, for system services, apps and agents, replacing `AppProfile`. **Tenancy has two levels**: the profile lists the modes it is certified for (`system`, `shared`, `tenant`); the instance carries the one mode the responsible admin chose, which must be in that list. `system` is exclusive. `shared` requires `trustTier: platform`, and `trustTier` stays in the spec so the rule is a CRD validation invariant rather than an admission policy. | [component-profile.md](component-profile.md) §1, §7 |
| AD-5 | **Requirements and integrations are separate fields.** A requirement is owed by the platform, gates admission, and its absence is the platform's fault; an integration is a peer relationship, bound continuously, absent peers normal. Privileges — egress beyond the baseline, pod-security waivers, elevated roles — are requirements with one approval path, so a profile cannot grant itself any of them. | [component-profile.md](component-profile.md) §3 |
| AD-6 | **Exposure carries a mandatory `authMode`** with no default, and a `surface` of `gateway` or `perimeter`. A perimeter surface is a capability the profile declares; a proxy exists in `tenant-<t>-dmz` only for a surface a **perimeter approver enabled**, within cluster policy, with that tenant's credential. The relation asked is `can_expose`, never `admin`, so publishing is always its own audit line; the tenant's admins hold that relation by default, because most tenants do not staff the role separately. Where the instance runs does not enter into it: shared and public are independent, and nothing is published by default. | [component-profile.md](component-profile.md) §5, [namespace-cleanup.md](namespace-cleanup.md) §2.6 |
| AD-7 | **Namespaces are named by tier**: `kernel-<function>`, `system-<function>`, `system-<function>-dmz`, `shared-<app>`, `tenant-<t>`, `tenant-<t>-dmz`. Tier-0 operators are kernel and are named by the function they perform (`kernel-provisioning`, not the product) so the software can change. Policies select on the labels `gentianos.io/tier` and `gentianos.io/function`, never on names. | [namespace-cleanup.md](namespace-cleanup.md) §1 |
| AD-8 | **Kernel trust domains are separate namespaces**: `kernel-authentication` (Keycloak, public route) apart from `kernel-authorization` (OpenFGA, enforcement points only); `kernel-seal` apart from `kernel-secrets`, because the seal's unseal key is an in-cluster Secret; kernel identity on its own Postgres in `kernel-data`, not on the tenants' data plane. | [namespace-cleanup.md](namespace-cleanup.md) §2.1 |
| AD-9 | **System services have no public route, without exception.** HTTP access from outside goes through a tenant's DMZ with that tenant's credential. A system service whose protocol needs an internet listener — mail, TURN — puts that listener in its own DMZ namespace, `system-<function>-dmz`, as a stateless edge holding one credential to the backend; a service that is all edge (TURN) lives there entirely. Data services are **one namespace per engine**, named by the function a requirement declares. vLLM is composed from the Cluster claim, not applied by the installer. | [namespace-cleanup.md](namespace-cleanup.md) §2.2, [networking.md](networking.md) §1 |
| AD-10 | **The portal splits two ways**: the tenant desktop — frontend bundle and its BFF, one image — runs in `tenant-<t>` with only that tenant's credentials; **the platform is a tenant** — `Tenant/platform` adopts the kernel realm, and the platform-admin console is that tenant's desktop in `tenant-platform`, the same image showing what the account's relations grant — admin tiles to an admin account, app tiles to a member account, never both: least privilege is per account, and administrator and member are disjoint roles ([roles-and-authorizations.md](roles-and-authorizations.md) §1). Nothing with authority leaves `kernel-control`; nothing without authority stays in it. The current single BFF holding every tenant's credentials is retired. Nothing of the portal is shared: the frontend holds no state, so serving it per tenant costs nothing and keeps it on the tenant's own origin; the BFF holds one tenant's UI state on one tenant's origin, which is exactly what AD-4 says a shared instance may not hold until certified. It holds no client secret: the edge is the only session authority (AD-13). | [namespace-cleanup.md](namespace-cleanup.md) §2.5, [ui-restructure.md](ui-restructure.md) §2 |
| AD-11 | The target layout applies to **fresh installs**. Stateful kernel components — OpenBao, Keycloak, CNPG clusters — are never renamed in place; an existing cluster rebuilds from its recovery kit or keeps its names and adopts the labels. | [namespace-cleanup.md](namespace-cleanup.md) §1 |
| AD-13 | **The edge is the only session authority.** One confidential OIDC client per tenant zone, on the `authenticated` Gateway, mints the one edge cookie; everything downstream consumes the forwarded token and runs no code flow of its own. Envoy Gateway's OIDC filter has no back-channel logout and keeps no server-side session, so **revocation lives on the ext-auth shim**: Keycloak's back-channel logout URI points at it, it records the revoked `sid`, and L2 denies it. The L2 decision cache is keyed on `(sub, sid, route)` — the session, not the token — so a refresh is not a miss and a revocation can be evicted. The hard bound on what a user may do *inside* an app is the app's own session, which a profile caps with `sessionMaxAge`; the edge bounds reachability, not an app's captured group model. | [networking.md](networking.md) §2, §4, [ui-restructure.md](ui-restructure.md) §1 |
| AD-12 | **The authorization store is a projection; Keycloak's events are the only source of membership in it.** Group membership is stored in OpenFGA as `group#member` tuples written by the director from Keycloak's event stream and reconciled toward Keycloak with a read-only client — never edited in place; contextual tuples carry runtime facts only (task TTL, `acting_for`, device posture). This is OpenFGA's own hybrid guidance and the Zanzibar shape: access reviews and reverse queries are native, checks are lookups, and no group travels in a token for a platform decision. Structure — role-to-group assignments, installs, grants, entitlements — is written by the director from CRs in the same operation as the commit it reflects; the store is rebuilt from Keycloak and git on start; the operator only reads it. The polling bridge with its admin credential is retired. The single vocabulary is [authorization-model.md](authorization-model.md). Because apps still read groups from their own tokens, **a membership change revokes the user's sessions**; access tokens stay short-lived and offline tokens are disabled. | [roles-and-authorizations.md](roles-and-authorizations.md) §3 |
