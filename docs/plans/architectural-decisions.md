# Architectural decisions

The decisions that set the direction of the architecture cleanup. Each one
is stated once here and referenced by number from the plans; the plans hold
the detail. A decision changes by editing its entry, not by contradicting
it elsewhere.

| # | Decision | Detail |
| --- | --- | --- |
| AD-1 | The nine rules in [security-principles.md](../security-principles.md) are normative. A change that breaks one needs a written reason. Every request passes exactly one named enforcement point — gateway, publishing proxy, director, custodian, MCP gateway — and apps never decide platform questions. | security-principles.md |
| AD-2 | The **director** is the only process that writes to `gentian-deployments`. Every write is authenticated by Keycloak and authorised by OpenFGA; commits are signed and Argo CD (`AppProject.spec.sourceIntegrity`, GnuPG mode `head`) syncs only commits signed by the director or the break-glass key. The **operator** writes to the cluster only and never holds a git credential. Git is thereby the trusted, audited source of cluster configuration. | [operator-split-plan.md](operator-split-plan.md) |
| AD-3 | **What lives outside the cluster is the App Store's data, not its interface.** The store is a service outside the cluster, run by a vendor. It holds and serves the data about apps: metadata, descriptions, pictures, reviews, evaluations and reports, editions and versions with their build digests, prices, and the record of what a tenant has acquired. The store's interface, and everything that happens when a button is pressed, are an app **on** the cluster: the **App Store app** (component `app-store`), a platform UI of its own, installed per tenant, its tile shown only to people who may install apps in that tenant. It renders what it fetches from the store's API, and it treats that content as data — plain text, a restricted Markdown subset, images by address — never as code: no HTML, no script and no frame from a store. It does the installing on the cluster's side, under the signed-in person's own token, through the director and the custodian, which ask of it what they ask of every other caller. **The cluster always calls out; the store never calls the cluster**, holds no credential for one, and has no page inside the cluster's interface. There is no message bridge between a framed vendor page and the cluster: that design is withdrawn, because it put a vendor's page and the logic of installing on the desktop, which is every member's app. **The store decides nothing for the cluster, and the cluster does no licence gating.** There are no entitlements: no statement a store signs, no store key pinned on a cluster, no relation for a tenant's right to an entry. **Supply is controlled at the source.** When a tenant acquires an app the store mints a credential for the repository that holds its chart and images, and that repository checks it on pull. The App Store app receives the repository's address and the credential in the store's confirmation, declares the repository through the director, sets the credential through the custodian, and installs with `{coordinate, digest, defaultGrant}`; a free app's confirmation carries no credential. The OS decides nothing in this: whether something has been paid for is the business of whoever sells it, and is enforced where the thing sold is handed over. A second copy of that decision inside the platform could only drift from the one that counts, and a platform meant to run with no store at all would have to switch a gate off rather than not have one. The director asks one question of an install — may this person install apps in this tenant (`can_install_app`) — and a second, `can_grant`, of an install made for everyone, which says so in the same request and the same commit (`defaultGrant` on the app's entry); the operator then grants the app to the tenant's members once, when its group exists. **Payment never passes through the cluster**: for a paid acquisition the store answers with a checkout address at the vendor, which the app opens in a separate window, and the app then asks the store for the outcome. **The digest still pins the build**: the store's confirmation carries the content digest of the profile bundle, the install request carries it, the bytes the cluster's own catalogue source serves are refused unless they hash to it, and the director records it in git as a field of the install — never as part of the app's name. The operator checks it again before it rolls anything out: the director commits the verified bytes beside the profile, and a Component pinned to a digest is rendered only when those bytes hash to it and the profile in the cluster is what they say. A store can therefore lie about what an app is and cannot change which bytes are installed. **The store depends on licence reporting** ([operations.md §6.2](../design/operations.md)): a cluster with reporting off has no App Store app. A tenant's administrator signs in to the store with an account at the vendor and states the address of the tenant; a store that has no reports for that address refuses, with a reason the app shows, and a cluster with no subscription is shown the terms of the free licence. Nothing on the cluster is blocked by any of it. **Without a store, apps are installed by command only** (AD-14). **Changed 2026-10-06** from "the App Store runs outside the cluster" as a whole — a vendor page in a window on the desktop, asking the desktop to install through a message bridge. What was right in it stays: the data is outside, the digest pins, the OS gates nothing. What changed is where the interface and the installing are. | [store-contract.md](../design/store-contract.md), the API format in [artefacts/store-api.md](artefacts/store-api.md) and [artefacts/store-api.openapi.yaml](artefacts/store-api.openapi.yaml), [ui-restructure.md](ui-restructure.md) §3, [target-component-structure.md](target-component-structure.md) |
| AD-4 | One catalogue kind, **`ComponentProfile`**, for system services, apps and agents, replacing `AppProfile`. **Tenancy has two levels**: the profile lists the modes it is certified for (`system`, `shared`, `tenant`); the instance carries the one mode the responsible admin chose, which must be in that list. `system` is exclusive. `shared` requires `trustTier: platform`, and `trustTier` stays in the spec so the rule is a CRD validation invariant rather than an admission policy. | [target-component-structure.md](target-component-structure.md) §1, §10 |
| AD-5 | **Requirements and integrations are separate fields.** A requirement is owed by the platform, gates admission, and its absence is the platform's fault; an integration is a peer relationship, bound continuously, absent peers normal. Privileges — egress beyond the baseline, pod-security waivers, elevated roles — are requirements with one approval path, so a profile cannot grant itself any of them. | [target-component-structure.md](target-component-structure.md) §4 |
| AD-6 | **Exposure carries a mandatory `authMode`** with no default, and a `surface` of `gateway` or `perimeter`. A perimeter surface is a capability the profile declares; a proxy exists in `tenant-<t>-dmz` only for a surface a **perimeter approver enabled**, within cluster policy, with that tenant's credential. The relation asked is `can_expose`, never `admin`, so publishing is always its own audit line; the tenant's admins hold that relation by default, because most tenants do not staff the role separately. Where the instance runs does not enter into it: shared and public are independent, and nothing is published by default. | [target-component-structure.md](target-component-structure.md) §8, [namespace-cleanup.md](namespace-cleanup.md) §2.6 |
| AD-7 | **Namespaces are named by tier**: `kernel-<function>`, `system-<function>`, `system-<function>-dmz`, `shared-<app>`, `tenant-<t>`, `tenant-<t>-dmz`. Tier-0 operators are kernel and are named by the function they perform (`kernel-provisioning`, not the product) so the software can change. Policies select on the labels `gentianos.io/tier` and `gentianos.io/function`, never on names. | [namespace-cleanup.md](namespace-cleanup.md) §1 |
| AD-8 | **Kernel trust domains are separate namespaces**: `kernel-authentication` (Keycloak, public route) apart from `kernel-authorization` (OpenFGA, enforcement points only); `kernel-seal` apart from `kernel-secrets`, because the seal's unseal key is an in-cluster Secret; kernel identity on its own Postgres in `kernel-data`, not on the tenants' data plane. | [namespace-cleanup.md](namespace-cleanup.md) §2.1 |
| AD-9 | **System services have no public route, without exception.** HTTP access from outside goes through a tenant's DMZ with that tenant's credential. A system service whose protocol needs an internet listener — mail, TURN — puts that listener in its own DMZ namespace, `system-<function>-dmz`, as a stateless edge holding one credential to the backend; a service that is all edge (TURN) lives there entirely. Data services are **one namespace per engine**, named by the function a requirement declares. vLLM is composed from the Cluster claim, not applied by the installer. | [namespace-cleanup.md](namespace-cleanup.md) §2.2, [networking.md](networking.md) §1 |
| AD-10 | **The portal splits two ways**: the tenant desktop — frontend bundle and its BFF, one image — runs in `tenant-<t>` with only that tenant's credentials; **the platform is a tenant** — `Tenant/platform` adopts the kernel realm and has a desktop in `tenant-platform` like every other tenant. **The desktop is the desktop, for everyone**: what differs between a platform administrator, a tenant administrator and a member is the tiles their relations grant, never the image. A member sees apps. An administrator sees the administration console, the App Store app, and links to what they administer — identity, the cluster dashboard, subscriptions — and never both sets: least privilege is per account, and administrator and member are disjoint roles ([roles-and-authorizations.md](roles-and-authorizations.md) §1). **The desktop is a relay for tiles**: it shows what the signed-in person may open and opens it. It carries no install, uninstall, add-on, access, repository or store logic, because it is the app of people who hold no privilege and must hold no administrative code path. **The administration console is an app**: a component installed for every tenant from its own profile and built from the app template, not a mode of the desktop; installed apps are administered there. **The App Store app is an app too** (AD-3): a platform UI of its own beside the desktop and the console, which renders the data of the store outside the cluster and installs through the director and the custodian. No page of a store is shown inside the cluster's interface, and the desktop is asked nothing on a store's behalf. A link to something that runs elsewhere is a component too, one that runs nothing and carries a tile. Nothing with authority leaves `kernel-control`; nothing without authority stays in it. The current single BFF holding every tenant's credentials is retired. Nothing of the portal is shared: the frontend holds no state, so serving it per tenant costs nothing and keeps it on the tenant's own origin; the BFF holds one tenant's UI state on one tenant's origin, which is exactly what AD-4 says a shared instance may not hold until certified. It holds no client secret: the edge is the only session authority (AD-13). | [namespace-cleanup.md](namespace-cleanup.md) §2.5, [ui-restructure.md](ui-restructure.md) §2 |
| AD-11 | The target layout applies to **fresh installs**. Stateful kernel components — OpenBao, Keycloak, CNPG clusters — are never renamed in place; an existing cluster rebuilds from its recovery kit or keeps its names and adopts the labels. | [namespace-cleanup.md](namespace-cleanup.md) §1 |
| AD-12 | **The authorization store is a projection; Keycloak's events are the only source of membership in it.** Group membership is stored in OpenFGA as `group#member` tuples written by the director from Keycloak's event stream and reconciled toward Keycloak with a read-only client — never edited in place; contextual tuples carry runtime facts only (task TTL, `acting_for`, device posture). This is OpenFGA's own hybrid guidance and the Zanzibar shape: access reviews and reverse queries are native, checks are lookups, and no group travels in a token for a platform decision. Structure — role-to-group assignments, installs, grants — is written by the director from CRs in the same operation as the commit it reflects; the operator only reads it. **Git holds the defaults, and everything beyond them is an action through the director.** The conventional tuples a tenant starts with — its admins group holding `admin`, the cluster holding `operated_by` — follow from what git declares, so they can be derived and checked; every later grant or revocation is an act somebody took, recorded when it happened and reconstructible from nothing else. The store is therefore not rebuilt on start: at bootstrap the director **checks that the defaults git implies are still the defaults the store holds** and reports the difference. A store that has diverged is a question, not a merge — rewriting it would erase exactly the acts that are not derivable. The polling bridge with its admin credential is retired. The single vocabulary is [authorization-model.md](authorization-model.md). Because apps still read groups from their own tokens, **a membership change revokes the user's sessions**; access tokens stay short-lived and offline tokens are disabled. | [roles-and-authorizations.md](roles-and-authorizations.md) §3 |
| AD-13 | **The edge is the only session authority.** One confidential OIDC client per tenant zone, on the `authenticated` Gateway, mints the one edge cookie; **no platform component downstream runs a code flow or holds a client secret**. The gateway forwards the edge token only on a route whose exposure entry sets `forwardToken` — the desktop, which needs it to call the director — and every other backend receives identity headers the gateway sets after stripping inbound ones; an app that keeps a session of its own runs a silent login with **its own client and audience**, so no app ever holds a token valid at the director or at a sibling. Envoy Gateway's OIDC filter has no back-channel logout and keeps no server-side session, so **ending a session at Keycloak is what ends it**: the edge holds a short-lived access token and refreshes it, and a refresh against an ended session fails. The bound on how long a signed-out person is still let through is the access token's lifetime, which the realm sets — so that lifetime is the control, and it is minutes rather than the twelve hours it once was. The director records nothing and the bouncer asks nothing: an earlier design had the director write `session:<sid>#revoked` for every bouncer replica to read, and it was removed because it cost a round trip on every request to answer a question the token's own expiry already answers. The cost of this choice is that sign-out is not instantaneous; the thing to change if that ever matters is the access-token lifetime, not the addition of a list. The L2 decision cache is keyed on `(sub, sid, route)` — the session, not the token — so a refresh is not a miss and a revocation can be evicted. The hard bound on what a user may do *inside* an app is the app's own session, which a profile caps with `sessionMaxAge`; the edge bounds reachability, not an app's captured group model. | [networking.md](networking.md) §2, §4, [ui-restructure.md](ui-restructure.md) §1 |
| AD-14 | **Without a store, apps are installed by command only.** `kubectl gentian apps install` asks the director, on the same route and under the same question as every other install (AD-3). **The cluster renders no catalogue of its own in any interface.** A second, barer shop beside the one that is maintained would be worse at everything a shop is for, and a listing with an install action in an administrative screen is one more place the logic of installing would live. A *catalogue source* remains what the director fetches from: a repository of profile bundles the platform administrator names on the Cluster claim, where the director fetches the bundle a coordinate names and checks it against the digest. A source publishes an index — coordinate, version, edition, trust tier, digest, and nothing a shop would show — and the director still answers it, the **ce** and **pe** entries only, so that an entry's digest can be looked up with no store; no screen lists it, and the console's catalogue view is hidden. A source the claim names can be installed from by **every tenant** of the cluster. Naming one is the platform administrator's act, a commit on the claim; there is no per-tenant list on a source and no tuple for it, because such a list gated nothing. It is not a licence, and there is no access mode a store sets on a source: the install itself is asked of the person and of nothing else (AD-3). One install mechanism (fetch the bundle at the digest, apply the profile, commit), whoever asked. **Changed 2026-10-06** from "the cluster lists its sources' entries as installable from its own screen". | [store-contract.md](../design/store-contract.md) §9 |
| AD-15 | **The OS is multi-lingual: every word a person reads is translatable**, and a language is added by adding a message catalogue, never by changing a component. German and English are the catalogues that ship today. Three surfaces, one rule. **The platform's own chrome** — desktop, console, Keycloak's login and account pages — carries a message catalogue per locale and no user-visible string is written inline in a component; Keycloak already ships translations, so its realms enable them rather than restating them. **A component's catalogue text** — the tile label today, and whatever else a person reads later — carries a required fallback plus an optional map keyed by locale (`de_DE`, `en_US`), which is additive: a profile with one language stays one line. **Matching is forgiving within a language and never across one**: `de-CH` is served `de_DE`, because a label in the viewer's language is better than one in another, while an unmatched language falls back to the author's own words rather than to a guess. The viewer's language comes from their account, and from the browser until they have said. A string with no translation renders its fallback — a missing translation is never a blank, an error or a key. | [ui-restructure.md](ui-restructure.md) |
